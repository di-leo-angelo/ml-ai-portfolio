# Qwen3 QLoRA: A Synthetic School Q&A Tutor

Fine-tunes **Qwen3.8-27B** with **QLoRA** (4-bit NF4 base + LoRA adapters)
so it answers school-level questions in a consistent tutor style: step by
step, concise, and verifiable. Training runs on a **rented GPU** (this
run: 48 GB 4090 for training, 24 GB 4090 for inference; RunPod / Vast.ai /
Lambda); the local machine only handles data generation, code, and the
small adapter that comes back.

**Scope: proof of concept.** This project demonstrates the *pipeline* -
synthetic data generation, QLoRA fine-tuning of a 27B model on a rented
24 GB GPU, and evaluation - not a production-grade tutor. The fine-tune's
primary goal is **tone transfer**: a consistent, step-by-step, concise,
self-checking tutor voice. Each subject's 150 samples form one topic cluster
around its committed seed (e.g. history = 150 variations of the WWI alliance
system, not 150 different historical events), with high surface diversity and
intentionally narrow topical coverage. Answer content is bounded by the
generator model's knowledge (see *Limitations*).

**Status: complete (2026-10-28/29).** The full dataset was generated and
split (1,500 samples; 1,120/150/230 train/dev/test; manifest in
`data/split.json`), a 20-sample content spot check found 0 factual or
arithmetic errors, the QLoRA training run completed on a rented 48 GB 4090
(72 min, 499 MB adapter), and the 255-generation test-set eval with
base-vs-LoRA comparison completed on a 24 GB 4090. All numbers in
*Results* and `reports/` are measured from the actual run, not estimates.

## Why this project

Full fine-tuning of a 30B+ model needs ~440 GB of GPU memory (bf16 weights
+ gradients + optimizer state). QLoRA keeps the base model in 4 bits
(read-only, ~17 GB) and trains only 0.45 % of the parameters, so the
fine-tune fits on a single rented card: this run peaked at ~30 GB during
training (48 GB 4090, 72 min, ~$2.60) and at 19.3 GB during inference
(standard 24 GB 4090). At ~$0.35-1.00/hour on GPU clouds a full training
run costs a few dollars, which makes iterating on data and hyperparameters
practical. The full memory arithmetic is in `reports/ANALYSIS.md`.

## The dataset: a generation recipe, not a download

The dataset is 100% synthetic - generated by a teacher model from the
committed seed prompts in `data/samples/seed_prompts.jsonl`. Nothing is
downloaded, so the dataset contains no external content and no personal
data. The recipe (subjects, difficulty mix, counts, prompts) is declared in
`src/qwen_qlora/config.py`:

| Setting | Value |
| --- | --- |
| Subjects | 10 (algebra, calculus, probability, chemistry, physics, biology, history, world geography, literature, computer science) |
| Samples | 150 per subject (1,500 total) |
| Difficulty | beginner / intermediate / advanced (rotated per sample) |
| Generator | any OpenAI-compatible chat API you have access to - public, self-hosted, or a private gateway with custom auth (default `gpt-4o-mini`; the validated run used `qwen-3.8-27b-nvfp4` via a private gateway) |
| Format | chat template: system (tutor persona) -> user -> assistant |
| Splits | 75/10/15, stratified by subject, fixed seed |

**What the code generates:** for each subject, the teacher model is asked to
write questions *topically similar but different* from the committed seed, so
the 150 samples per subject form a **topic cluster around that seed**
(different numbers, contexts, and framings at three rotated difficulty
levels) - not 150 distinct topics. All 1,500 questions are unique (the
generator rejects and regenerates duplicates), and the consistent formatting
across a subject's cluster is what the fine-tune uses to transfer tone.

### Regenerate

```powershell
# 1. Copy .env.example to .env and set OPENAI_API_KEY
uv run python projects/qwen-qlora/scripts/generate_data.py
uv run python projects/qwen-qlora/scripts/prepare_data.py
```

Generation is resumable (per subject) and idempotent (de-duplicated by
question). Each sample uses a unique per-sample prompt variation, and any
generated question that duplicates an existing one is rejected and
regenerated, so the raw file never contains duplicate questions.
`--concurrency N` runs N parallel API calls (default 1). `data/split.json`
records sizes and SHA-256 hashes so any dataset can be fingerprinted.

## Hardware and renting

| GPU | VRAM | Fits |
| --- | --- | --- |
| RTX 4090 | 24 GB | Yes - 4-bit 27B (~17 GB) + LoRA states + activations at 2048 sequence length |
| RTX 5090 | 32 GB | Comfortable, faster (longer sequences / larger batches) |
| A6000 / L40S | 48 GB | Plenty of headroom |

Practical workflow:

1. Rent a pod with a visible GPU (e.g. RunPod RTX 4090, 150 GB disk, recent
   PyTorch template).
2. `pip install -r projects/qwen-qlora/requirements-gpu.txt` (GPU-only deps,
   kept out of the main environment).
3. Inside `tmux`, run `scripts/download_model.py` first so the base model is
   cached in `models/` before the training job starts.
4. Copy the repo + prepared `data/*.jsonl` to the pod (`scp` / git).
5. `cd projects/qwen-qlora && python src/qwen_qlora/train.py --model-name
   models` - keep it inside tmux so a disconnect does not kill the run.
6. Copy the trained adapter (`artifacts/`, a few hundred MB) back, then stop
   the pod.

## Method

| Setting | Value |
| --- | --- |
| Base model | Qwen/Qwen3.8-27B (Apache-2.0, 27.8B; hybrid 48 linear-attention + 16 full-attention layers, vision tower frozen/unused) |
| Quantization | bitsandbytes NF4, double quantization, bf16 compute |
| LoRA | r=16, alpha=32, dropout 0.05, on all linear layers (vision tower, MTP head, and LM head excluded) |
| Training | hand-rolled SFT loop (no TRL): bf16 autocast, gradient checkpointing, effective batch 8 (1 x 8 accum), 2 epochs, cosine LR 2e-4 with 3% warmup, best-dev-loss saving |
| Sequence length | 1024 (longest sample is ~450 tokens; 2048 would waste ~4x compute) |
| Evaluation | eval loss per epoch on the 150-sample dev split + a side-by-side generation report on the 230-sample test split |

The trained artifact is the LoRA adapter only (a few hundred MB); the base
model is never modified.

## Results

Measured from the 2026-10-28/29 run (training: 48 GB 4090; inference eval:
24 GB 4090). Full reports: `reports/auto_eval/summary.md`,
`reports/base_vs_lora/comparisons.md`, `reports/eval_report.txt`.

| Stage | Measured |
| --- | --- |
| Training | 72 min 10 s, 280 steps; best dev loss 0.3671 at epoch 1 (epoch 2: 0.3691, no improvement → epoch-1 adapter kept); peak ~30 GB |
| Adapter | 499 MB — 124.7 M trainable params = **0.454 %** of the 27.48 B model |
| Inference | 255 test-set generations (230 LoRA + 25 base), peak 19.3 GB on the 24 GB card (4.7 GB headroom) |
| Auto-grade (n=230) | **45 % exact match** (52/115) on answer-format questions; **92 % of answers within the ~350-word tutor budget** |
| LLM judge (n=245, Qwen3-32B-AWQ) | mean 4.8 / 4.0 / 4.2 (correctness / format / completeness); saturates at 5.0 on STEM, weakest on humanities |
| Base vs LoRA (first 25 test samples, paired) | same answers in the trained voice: the adapter transfers the step-by-step, self-checking tutor *format* without changing the base model's knowledge |

How to read this: the fine-tune's goal is **tone transfer, not knowledge
injection** (see the scope note above). The 45 % exact-match rate is the
*base model's* knowledge ceiling on these questions — CS (13 %) is the base
model's weakness, not the adapter's. LLM-judge scores are lenient by
construction (a 32B judge saturates on plausible STEM reasoning), so the
stricter signals are exact-match and word-budget compliance: 92 % of the
fine-tuned model's answers respect the tutor's hard word budget, and the
paired comparisons show it doing so in the trained step-by-step voice.

Eval pipeline (all committed): `scripts/eval_run.py` (GPU, resume-safe) →
`scripts/auto_grade.py` + `scripts/judge_run.py` (CPU / LLM-as-judge) →
`scripts/make_base_vs_lora.py` (CPU, paired report).

## Limitations

- Synthetic data: the model learns the *style and format* of the generator;
  knowledge quality is bounded by the generator model. Spot-checking a sample
  of the generated Q&A before training is worthwhile (the generated dataset
  used for this project passed a 20-sample spot check with 0 factual or
  arithmetic errors).
- Topic anchoring: each subject's 150 samples are generated from a single
  committed seed prompt and stay topically close to it (e.g. all history
  samples concern the WWI alliance system). Surface diversity is high
  (different numbers, contexts, framings), but topical coverage per subject
  is narrow; expanding `data/samples/seed_prompts.jsonl` to several seeds
  per subject and rotating across them broadens coverage.
- Difficulty labels are assigned by the generator model and run a bit
  generous: "advanced" typically means solid high-school level rather than
  genuinely challenging. The three tiers are internally ordered.
- LLM-as-judge scoring (Qwen3-32B-AWQ on 245/255 samples) is lenient by
  construction: a 32B judge saturates near 5.0 on plausible STEM reasoning,
  so exact-match and word-budget compliance are the stricter signals; the
  judge is reported for format/completeness comparison, not as accuracy.
  10/255 samples could not be parsed into scores and are excluded, with
  coverage reported in the summary.
- Single GPU with micro-batch 1 keeps the effective batch modest (8); a
  multi-GPU run could use a larger effective batch and more epochs.
